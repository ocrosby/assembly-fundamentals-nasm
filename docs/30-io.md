# File I/O

The [`libio`](../libs/io/) archive covers every syscall
between a caller and a file — `open`, `pread`, `pwrite`,
`lseek`, `mmap`, and the metadata and directory ops in
between. Once callers have written the "open + short-write
loop + close" boilerplate a few times, the same shape starts
to appear everywhere. libio's `util/` folder collects those
shapes as one-call helpers. This chapter surveys the four
that ship today.

## The I/O family

| Helper           | Shape                                     | Use case                                   |
| ---------------- | ----------------------------------------- | ------------------------------------------ |
| `file_read_all`  | Return `PROT_READ` mapping + size         | "Give me this file as a buffer."           |
| `file_write_all` | Truncate and replace                      | "Dump this buffer as the whole file."      |
| `file_append`    | Open with `O_APPEND`, add to end          | "Grow this file with more records."        |
| `file_copy`      | Two mmaps, `rep movsb` between them       | "Duplicate this file to another path."     |

Each returns `0` on success or a negative errno on failure.
Each is self-contained — no libc, no libstr, and no libsock
coupling. `close` is inlined via raw syscall the same way
`dir_iter_close` does, so callers who need file I/O without
sockets link only `libio.a`.

## The O_TRUNC vs O_APPEND distinction

`file_write_all` and `file_append` share almost the same
program: open the destination, write bytes in a short-write
loop, close. The one difference is the open flag mask.

- `file_write_all` opens with `O_WRONLY | O_CREAT | O_TRUNC`.
  Any existing content at `path` is discarded before the
  first write.
- `file_append` opens with `O_WRONLY | O_CREAT | O_APPEND`.
  Every write on this fd atomically seeks to the current
  end of the file before writing.

That single flag is what turns "replace the file" into "add
to it." The
[`41-logger`](../examples/41-logger/) example uses
`file_write_all` for the first record (to guarantee a clean
slate) and `file_append` for every record after — a real
log writer's shape in miniature.

## The `file_read_all` ownership contract

`file_read_all` mmaps the source file `PROT_READ MAP_PRIVATE`,
closes the underlying fd, and hands the caller the mapping
address and size. The mapping outlives the fd on both
platforms (the kernel keeps an internal vnode reference), so
callers never see an open file descriptor for the file — only
the read-only view.

Ownership passes to the caller: `libio` does not attach a
finalizer or track the allocation. When the caller is done
walking the bytes, it calls `munmap(addr, size)`. Zero-length
files return `addr = NULL, size = 0` so callers get a
distinctive sentinel rather than a platform-specific
`mmap(len=0)` failure. The
[`37-config-load`](../examples/37-config-load/) and
[`39-number-store`](../examples/39-number-store/) examples
walk this end to end.

## Short writes are the caller's problem

The kernel is allowed to return fewer bytes than requested
from every `write(2)` call. libio handles this by looping in
userspace until the whole payload has landed — the same
pattern `libsock`'s `send_all` uses for sockets. Any error
mid-way returns the negative errno through the close cleanup.
Callers see either "all bytes written, return 0" or "some
error, return -errno" — never a partial success.

## What isn't a libio helper

- **Random-access read/write.** `pread` and `pwrite` are
  syscall wrappers, not composed helpers — the "read all"
  and "write all" shapes are what most callers actually
  need. Callers who want fine-grained offsets use the
  wrappers directly.
- **Streaming copy to a socket.** `file_copy` targets a
  destination path, not an fd. A `file_copy_stream` helper
  (source path → open fd) may join the family once a
  concrete consumer needs it — see the feature-skeptic
  guard in `~/.claude/rules/feature-skeptic.md`.
